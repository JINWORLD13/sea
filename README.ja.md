## 🚢 プロジェクト概要

**実際の全世界AIS（Automatic Identification System）リアルタイムデータ**を基にした船舶管制インターフェース（モックデータではない）。AISStream.io の位置ストリームを Node プロキシ経由で受信し、クライアント側で衝突リスク（CPA/TCPA）を計算して、Leaflet マップと Three.js の 3D ビューに数百隻を描画する。

中心的な技術課題は、**毎秒数百件で到達するストリームを、ブラウザが描画できる速度まで落とすこと**。プロキシ → ストリーム → ストア → 描画の4層バックプレッシャーパイプラインで解決した。

## 🌟 主要機能

1. **リアルタイムAISマップインターフェース**
   - 船舶のHeadingデータに基づいたカスタムマーカー回転システム
   - 船舶の航跡（直近の移動経路）の視覚化と針路ベクトルの表示
   - 危険度別の色分け（safe / warning / danger）とジオフェンシング（制限水域）のハイライト

2. **3D船舶ビュー**
   - Three.jsおよびReact Three Fiberによる3D船舶レンダリング
   - 実際に受信する方位（heading）と速度を Lerp 補間で滑らかに反映
   - 注記: AIS 規格には pitch/roll の情報が存在しないため、3Dビューは実際に受信する値のみを反映する

3. **衝突リスク分析（CPA/TCPA）** — *式ではなく、その式を包む部分が本体*
   - CPA/TCPA は相対速度ベクトルの二次式なので **実装は 15 行**。時間を費やしたのは、実データで包んだときに崩れる箇所だった
   - **座標系** — 緯度経度をそのまま引くと、釜山（35°N）で東西距離を **22% 過大評価**する。経度差に `cos(基準緯度)` を掛けてメートルへ補正。**経度 0.005° は実際には 455m だが、無補正では 556m と計算され danger を丸ごと取り逃がす**
   - **数値的例外** — 同一針路・同一速力では相対速度が 0 になり TCPA の分母が消える。**相対速度の二乗が `1e-6` 未満なら現在距離で代替する**
   - **誤警報の遮断** — TCPA の符号と時間地平を併せて判定。**最接近点を通過した船は 50m 隣でも safe**
   - **欠測値を捏造しない** — COG・heading の両方が欠けている場合（Class-B に多い）、**0° を既定値にせず停止として扱う**。「真北へ航行中」という架空のベクトルを遮断する
   - **警報のフラッピング抑制** — **進入 500m / 解除 650m のシュミットトリガー** + **降格のみ 20 秒の猶予（昇格は即時）**。点くのは速く、消えるのは遅く（warning 等級も CPA 1,500m・TCPA 12 分の地平に同じ方式で適用される）
   - **検証** — 判定ロジックを描画から独立した**純粋関数**として分離し、航海の遭遇状況を**ゴールデンケース**として固定。**Vitest 42 件が通過**
   - 2秒周期の CPA/TCPA スキャン（自船基準の O(n)）

4. **ジオフェンシング**
   - 釜山の制限水域への進入時に自動警報 — 進入した船舶は**オレンジの外郭線・グロー**で即座に判別できる

5. **運用モード**
   - Fleet / Safety / Marina のモード切替 — それぞれ登録船隊フィルタ、全体アラートフィードの監視、7ノット未満の小型船フィルタ
   - Analytics は過去データではなく現在のセッションの集計であり、画面にもその旨を明記している

6. **高性能な状態管理**
   - Zustand のセレクター購読 + copy-on-write 更新
   - 1秒バッチ flush、画面ごとの 700〜1,200ms スナップショットスロットル + `startTransition`
   - ビューポートカリング → マーカー250個上限 → ズーム12未満はピクセルグリッドクラスタリング
   - マーカーの移動は共有 rAF ティッカーで補間し、**React の再レンダリングはゼロ**

7. **グローバル対応**
   - i18nextを活用した韓国語、英語、日本語の多言語対応（ブラウザ言語の自動検出）

## 🚀 スタートガイド

1. リポジトリをクローンする。

   ```bash
   git clone https://github.com/JINWORLD13/sea.git
   ```

2. 依存関係をインストールする。

   ```bash
   npm install
   ```

3. 環境変数を設定する。(.env)

   ```
   AISSTREAM_API_KEY=your_api_key_here
   ```

   > `VITE_AISSTREAM_API_KEY` では**なく** `AISSTREAM_API_KEY` を使う。
   > Vite は `VITE_` 接頭辞の変数をクライアントバンドルにそのままインライン展開するため、
   > devtools を開いた誰にでもキーが露出する。キーが必要なのはプロキシプロセスのみで、
   > プロキシは `VITE_` 接頭辞の名前をそもそも読まない実装になっている。

   > ポートは両側とも 8080 が既定。8080 が使用中の場合は `PROXY_PORT` と
   > `VITE_PROXY_PORT` を**同じ値**（例: 8081）で併せて設定する — 前者はプロキシの
   > ポートを移し、後者はフロントの接続先を知らせる。

4. フロントエンドとプロキシサーバーを同時に起動する。

   ```bash
   npm run dev
   ```

### データフロー

**フロント ↔ プロキシサーバー ↔ AISStream** — WebSocket双方向通信。フロントから購読リクエスト（例：BoundingBoxes）をサーバーに送ると、サーバーがAISStreamへ転送し、AISデータはAISStream → サーバー → フロントへストリーミングされる。

### ワイヤープロトコル（プロキシ → フロント）

AISStream の生メッセージをそのまま中継せず、`t` フィールドで判別する独自プロトコルを定義して配信する。フロントは AIS 規格を知らないまま、整形済みの JSON だけを扱えばよい。

| `t` | ペイロード | 発生タイミング・頻度 |
| --- | --- | --- |
| `pos` | `mmsi, lat, lng, sog, cog, hdg, nav, name, kind, ts` | 位置報告（Msg 1/2/3/18/19/21）ごと・高頻度 |
| `static` | `mmsi, name, imo, callsign, type, dest, eta, length, width, draught, ts` | 静的報告（Msg 5/24）ごと・約6分周期 |
| `snapshot` | `ships: [...]` — 位置と静的情報をフラット化して統合した配列 | 接続・再購読の直後に1回・100隻チャンク |
| `snapshotEnd` | `total` | スナップショットのチャンクがすべて送り終わったことを通知 |
| `error` | `error, message` | 購読検証の失敗など（`BOUNDING_BOX_TOO_LARGE` などのコードで区別） |

クライアント → プロキシ方向は購読メッセージ1種類のみ： `{ "BoundingBoxes": [[[minLat, minLng], [maxLat, maxLng]]] }`

**なぜこう分けたか** — 3つの基準で設計した。

1. **変化の頻度で分離した。** 緯度経度・速力は秒単位で変わるが、船名・IMO・船種・寸法は数時間に一度しか変わらない。一塊で送ると変化しないデータを毎秒再送することになるため `pos` / `static` に分け、フロント側で MMSI をキーとする `Map` に統合している。
2. **ドメインの解釈はサーバーで完結させる。** AIS のセンチネル値（SOG 102.3 = 不明、COG 360 = 不明、Heading 511 = 不明、ShipType 0 = 不明、ETA `00-00 24:60` = 不明）はすべてサーバー側で `null` に変換する。6ビット文字列の `@` パディング除去、MMSI 接頭辞による分類（`00`=基地局、`99`=航路標識）もサーバーの担当。結果としてフロントのコードから AIS プロトコルのパース処理が完全に消えた。
3. **バイト数よりメッセージ件数のほうが高くつく。** フレームのオーバーヘッド・イベントループ・React の再レンダーはいずれもメッセージ件数に比例するため、スナップショットは100隻チャンクに分割して単一の巨大フレームを避け、フロントは1秒バッチ flush で個々の `pos` をまとめ、ストアへの書き込み1件に集約する。

### セキュリティ

- **サーバー → AISStream**: API キーは **WSS**（`wss://stream.aisstream.io`）のみで送信し、AIS URL が `wss://` でなければサーバーは起動を拒否する。
- **ブラウザ → プロキシ**: HTTPS で配信されればプロキシ接続も **wss://** を使用する。キーがブラウザへ渡ることはない。
- **クライアント入力を信頼しない**: プロキシはすべてのクライアントメッセージを検証する — オブジェクトでないペイロードや範囲外座標は拒否、フレームサイズは 64KB 上限（`ws` 既定の 100MB を置換）、購読フラッドは 300ms ごとに最新 1 件へ集約、30秒の ping/pong ハートビートでハーフオープン接続を整理。本番では `ALLOWED_ORIGINS` で接続可能な Origin をフロントのドメインに制限できる。

## 💡 技術的課題と解決策

### 1. 高頻度 WebSocket データの処理最適化

- **課題**: 大量のAISデータ（数百隻の船舶）がリアルタイムで流入する際、マップマーカーのちらつきや全体のパフォーマンス低下が発生した。
- **解決策** — 4層のバックプレッシャーパイプライン。各層が異なる種類の負荷を吸収する。
  - **プロキシ（`server/proxy.js`）**: 購読ボックスの面積を 0.25 平方度以下に強制検証、クライアントごとに毎秒180メッセージ・追跡600 MMSI の上限、5,000隻のサーバーキャッシュから100隻チャンクで即座にスナップショットを配信。
  - **ストリーム（`aisStream.ts`）**: MMSI をキーとする `Map` に統合して1秒間隔でバッチ flush。同一船舶の連続報告がストア書き込み1件に集約される。
  - **ストア（`useShipStore.ts`）**: 追跡500隻の上限と20分無受信の自動整理。CPA/ジオフェンスを**単一パスの copy-on-write** で計算し、船舶ごとに発生していた全体コピーと購読者通知を**最大1回**に削減。
  - **描画（`useShipSnapshot.ts` + `map/`）**: 画面ごとに 700〜1,200ms のスナップショットスロットルを `startTransition` 内で実行し、画面外をカリングした上でマーカーを250個に制限、ズーム12未満は64pxのピクセルグリッドでクラスタリング。

### 2. 再レンダリングなしでマーカーを滑らかに動かす

- **課題**: AIS の位置報告は数秒〜数十秒の不規則な間隔で届くため、マーカーが瞬間移動する。かといって React の state で補間すると、毎秒60回 × 250個の再レンダリングが発生する。
- **解決策**:
  - **共有 rAF ティッカー**（`markerAnimation.ts`）: すべてのマーカーが `requestAnimationFrame` ループ**1つ**を共有し、`layer.setLatLng()` で Leaflet レイヤーを直接操作 → **React の再レンダリングはゼロ**。進行中の補間がなければティッカーは自動的に停止する。
  - **不連続区間のスナップ**: 500m を超えるジャンプ（信号消失からの復帰）は補間をスキップし、船が海を横切って滑るように見えるのを防ぐ。
  - **負荷に応じた段階的低下**: ズーム11未満、またはマーカー150個超では補間を無効化し、OS の `prefers-reduced-motion` 設定を尊重する。
  - **海上数学**: COG（対地針路）・SOG（対地速力）を速度ベクトルへ変換するユーティリティを作成し、CPA 計算に使用している。

### 3. React StrictMode でソケットがゴーストとして残る問題

- **課題**: StrictMode のエフェクト二重実行により、破棄したはずの旧ソケットが生き残り、`onmessage` がストアへ書き込み続け、再接続タイマーが発火し続けてデータ重複と再接続の暴走が発生した。
- **解決策** — **世代（generation）カウンター**（`aisStream.ts`）:
  - `startAisStream`/`stopAisStream` が `streamGeneration` を**先にインクリメントしてから**その値をキャプチャする。全コールバックは自分の世代が最新かを確認して即座に return するため、旧世代のコールバックはすべて no-op になる。
  - `onclose` も同じ判定で**意図的な終了と予期しない切断を区別**し、後者のみ再接続をスケジュールする。
  - 終了時は**順序**が重要 — `activeBounds` を `null` にする前に残りのバッチを flush してキャッシュを保存する必要がある（キャッシュが bounds でフィルタリングするため）。
  - 再接続は指数バックオフ（1秒 → 30秒上限）に ±20% のジッターを加え、**既存の船舶リストは保持**して画面が空にならないようにしている。

### 4. 大量の船舶をリアルタイム描画するとマップのズーム/クリックが重くなる問題

- **課題**: グローバルAISストリームでマーカー/ポップアップ/SVGアイコンを過剰に描画し、マップのスクロールズーム、クリックフォーカス、パンの応答が大きく低下した。
- **解決策**:
  - **ビューポート基準の描画**: 現在のマップ画面（bounds）内の船舶のみを描画するように変更した。
  - **描画上限の適用**: 一度に描画する船舶数を制限（`MAX_RENDERED_SHIPS`）し、中心に近い船舶を優先表示するようソートした。
  - **アイコンキャッシュ最適化**: 船舶アイコン（`DivIcon`）をキャッシュして再生成コストを削減しつつ、実際の heading 回転は維持した。
  - **自動ビュー調整の改善**: 初回表示時のみ自動フィット（`fitBounds`）し、選択・手動フォーカス中は自動移動をスキップするようにした。

### 5. まだ情報のない船舶の扱い

- **課題**: AIS は**位置メッセージ（数秒間隔）**と**静的メッセージ（5〜6分間隔）**が分離されており、到着順も保証されない。画面に入ってきたばかりの船は座標はあるが、船名・IMO・目的地がない。
- **解決策**:
  - 位置より先に届いた静的情報は MMSI ごとに保留（最大300件、古いものから追い出し）し、位置が到着した瞬間にマージする。
  - マージ規則を意図的に非対称に設計した — **静的フィールドは情報を「追加」するだけで `null` では消さない**（報告種別によってフィールドが正常に欠落するため）。一方、針路・方位のような動的フィールドは明示的な `null` を受け入れ、古い値が画面に残らないようにする。
  - 位置のない静的情報だけでは船舶を生成せず、座標 (0, 0) のゴーストマーカーを防ぐ。
  - 値が不明なときはもっともらしい既定値で埋めず「不明」と表示する。

### 6. 衝突リスク判定を「信頼できるもの」にする

- **課題**: CPA/TCPA の式そのものは相対速度ベクトルの二次式であり、15 行で終わる。難しいのは式ではなく、**その式を実データで包んだときに崩れる箇所**だった。AIS は欠測が多く、座標は角度であり、値は毎秒揺れる。
- **解決策** — 5 つの論点をそれぞれコードで処理した。
  - **座標系** (`latLngToXY`): 緯度経度をそのまま引くと、釜山（約 35°N）で東西距離を約 22% 過大評価する（`cos 35° ≈ 0.819`）。局所平面へ投影し、経度差に `cos(基準緯度)` を掛けてメートルに合わせた。500m のしきい値ではこの補正ひとつが判定を変える — 経度 0.005° の差は実際には 455m だが、補正を外すと 556m と計算され danger を丸ごと取り逃がす。
  - **数値的例外** (`calculateCPA`): 同一針路・同一速力では相対速度が 0 になり、TCPA の分母が消える。相対速度の二乗が `1e-6` 未満なら現在距離を CPA として用いる。最接近点が過去の場合（`tcpa < 0`）も同じ経路へ落とす。
  - **誤警報の遮断**: 距離だけを見ると、すでに最接近点を通過して離れつつある船まで danger になる。**TCPA の符号と時間地平を併せて**見ることで、いま対応が必要な遭遇だけを危険と判定する。
  - **欠測値を捏造しない** (`cpaVelocity`): COG と heading の**両方**が欠けている場合（Class-B 小型船に多い）、0° を既定値にせず停止として扱う。プロキシがセンチネル値（COG 360、heading 511）を正直に `null` へ正規化しているのに、ここで 0° を埋めると**「北へ航行中」という存在しないベクトル**が警報を汚染する。
  - **警報のフラッピング抑制** (`riskGrading.ts`): CPA がしきい値付近で数メートル揺れるだけで、判定はスキャンごとに反転する。進入線（500m）と解除線（650m）を分けたシュミットトリガーを入れ、**降格にのみ** 20 秒の猶予を置いた。点くのは速く、消えるのは遅く — 警報においてこの二方向は対称ではない。
- **検証**: 判定処理全体をレンダリングから切り離した純粋関数として抽出し、実際の遭遇状況（正面対勢・直角横切り・追い越し・停止目標・並航・離隔中）をそのままゴールデンケースに移した。ストアの危険度判定パスも併せて覆っている — ジオフェンスの進入エッジと判定履歴の寿命は、もっともらしい修正が回帰を生むまさにその箇所だからだ。Vitest 42 件が `npm test` で通る。
  - 分離した理由: **海上数学は目視で検証できない。** 画面がもっともらしく見えていても、22% ずれた距離で警報を出している可能性があり、それはスクリーンショットには現れない。

## ⚠️ 既知の制限

意図的な選択であり、明記しておく。

- **AIS 規格には pitch/roll の情報がない。** 以前のバージョンでは 3D ビューで船体動揺を表現していたが、実データの裏付けがないことを確認して削除した。現在の 3D ビューは方位と速度のみを反映する。
- **燃料消費量・CO2 排出量の推定機能も同じ理由で削除**した。AIS からは算出できない値であり、根拠のない数値を管制ダッシュボードに表示することは、数値がないことより危険である。
- **Analytics は過去データではなく、現在のセッションで追跡した船舶の集計**であり、画面上にもその旨を表記している。
- **サーバーキャッシュはインメモリ**のため、プロキシ再起動時に失われる。複数インスタンスへ拡張するには Redis のような外部ストアが必要。
- **推測航法（dead reckoning）の補間は未適用**。AIS の更新周期は錨泊3分・低速10秒・高速2秒とばらばらで、錨泊船と通信の途絶えた船が画面上で同じに見える。最後の COG・SOG から位置を補間し、一定時間未受信なら stale として薄く表示するのが次の課題。
- **ヒステリシス定数（解除線 1.3 倍、降格猶予 20 秒）は実測ではなく判断で決めた値**である。フラッピングの解消と、危険が去ってから警報が消えるまでの遅さとの折衷であり、実際の管制運用ログなしでは最適値が分からない。
- **CPA 判定は点基準**である。実際の危険は船の長さ・幅を考慮した船体間距離で見るべきである。
- **COLREG の遭遇状況を未分類**。正面・追い越し・横切りで避航義務が異なるが、現状は距離と時間のみを見ている。
- **時系列ストアがない**。長期の航跡再生・統計には別途ストアが必要。
- **性能数値は未計測**。最適化の前後を FPS・フレームタイム・秒間処理メッセージ数として残すことが残っている。
